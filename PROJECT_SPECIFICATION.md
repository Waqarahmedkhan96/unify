# Unify ERP — Project Specification

> **Product:** Unify  
> **Tagline:** A cross-platform ERP solution focused on performance, scalability, and offline-first capabilities.  
> **Document type:** Complete project specification  
> **Primary platforms:** Android and Windows  
> **Core stack:** Flutter, Dart, ASP.NET Core, C#, Entity Framework Core, PostgreSQL, Drift, SQLite, Docker, GitHub Actions

# Part 1 — Executive Summary, Vision, Problem Domain, Problem Statement, Scope, and Stakeholders

## 1. Executive summary

Unify is a secure, modular, multi-tenant, offline-first Enterprise Resource Planning platform designed for small and medium-sized businesses.

The platform will provide one connected system for managing:

- organisations;
- branches;
- warehouses;
- users;
- roles;
- permissions;
- devices;
- customers;
- suppliers;
- products;
- services;
- pricing;
- quotations;
- sales orders;
- invoices;
- sales returns;
- customer payments;
- customer credit;
- accounts receivable;
- purchase requests;
- purchase orders;
- goods receipts;
- supplier invoices;
- supplier payments;
- accounts payable;
- inventory;
- stock transfers;
- stock counts;
- device stock allocations;
- expenses;
- cash accounts;
- bank accounts;
- wallet accounts;
- accounting;
- fiscal periods;
- deliveries;
- employees;
- attendance;
- leave;
- payroll;
- assets;
- reports;
- audit history;
- offline synchronization;
- conflict management.

Unify will support Android and Windows from one main Flutter codebase. Each device will include a local SQLite database managed through Drift, allowing approved business operations to continue for several hours without internet access.

The central backend will use ASP.NET Core Web API with C#, Entity Framework Core, ASP.NET Core Identity, PostgreSQL, JWT access tokens, rotating refresh tokens, policy-based authorization, structured logging, audit history, Docker, and GitHub Actions.

Royal LPG will be the first organisation using Unify. LPG-specific behavior will be implemented as an optional industry extension rather than being hard-coded into the ERP core.

## 2. Product vision

The vision of Unify is to give businesses one reliable and connected source of operational and financial truth.

The product should allow a business owner to answer questions such as:

- How much did we sell today?
- How much was cash, credit, bank, Easypaisa, or JazzCash?
- Which customers still owe money?
- Which supplier invoices are unpaid?
- What stock is available?
- What stock is allocated to offline devices?
- What did each branch sell?
- What are today’s expenses?
- What is the difference between expected and actual cash?
- What is gross profit?
- What is net operating result?
- What is the cash-flow position?
- Which employee created, edited, reversed, or approved a transaction?
- Which transactions are pending synchronization?
- Which offline operations are in conflict?
- Which accounting entries were generated by each source transaction?

Unify should feel simple in daily use while enforcing strict data integrity, security, accounting, audit, and synchronization rules.

## 4. Problem domain

Many small and medium-sized businesses use separate tools for:

- customers;
- sales;
- purchases;
- inventory;
- suppliers;
- expenses;
- payments;
- accounting;
- reporting.

Common tools include:

- handwritten registers;
- Excel files;
- WhatsApp messages;
- paper invoices;
- separate mobile apps;
- verbal approvals;
- shared passwords;
- manual stock counting.

These systems are disconnected.

A single business event may need to affect multiple areas.

Example:

```text
Customer sale
    ↓
Inventory decreases
    ↓
Revenue is recorded
    ↓
Cash or receivable is recorded
    ↓
Customer history is updated
    ↓
Audit history is created
    ↓
Accounting journal is posted
```

When these records are maintained separately, mistakes become likely.

---

## 5. Problem statement

Businesses using manual or disconnected systems face problems such as:

- missing sales;
- duplicate sales;
- duplicate payments;
- incorrect customer credit;
- forgotten customer payments;
- incomplete customer history;
- incorrect supplier balances;
- incomplete purchase history;
- inaccurate stock;
- hidden negative stock;
- untracked stock adjustments;
- no branch-level visibility;
- weak device control;
- shared credentials;
- unauthorised access;
- deleted or edited financial records;
- no audit trail;
- difficult profit calculation;
- confusion between profit and cash flow;
- manual monthly and yearly reports;
- inability to work during internet failure;
- duplicate synchronization after retry;
- conflicting edits;
- two offline devices selling the same stock;
- outdated prices used offline;
- no tested backup process;
- no disaster recovery plan.

Unify is intended to solve these problems by combining operational modules with secure authentication, permission-based authorization, append-only financial corrections, double-entry accounting, device stock allocation, offline outbox/inbox synchronization, and central reporting.

## 10. Assumptions

- Each approved device has enough storage for its assigned local data.
- The first release will use one central PostgreSQL database.
- Official reports require synchronized data.
- Offline reports are provisional.
- Each organisation has a configured base currency.
- Server timestamps are stored in UTC.
- Display timestamps use the organisation’s timezone.
- Financial transactions use decimal-safe values.
- Offline stock selling requires stock allocation.
- Production deployments use HTTPS.
- Google Play rules will be checked at release time.

---

## 11. Constraints

- One Flutter codebase must support Android and Windows.
- Flutter clients must not connect directly to PostgreSQL.
- Financial records must remain auditable.
- Offline synchronization must be idempotent.
- Multi-tenancy must be enforced by the backend.
- Modules must remain inside a modular monolith initially.
- Production secrets must not be committed.
- User permissions must be enforced by the API.

## 13. Architectural style

Unify will use a modular monolith.

Benefits:

- simpler deployment;
- simpler debugging;
- lower infrastructure cost;
- easier transactions;
- easier development for a small team;
- clear future extraction points.

Module boundaries must be respected.

---

## 14. Multi-tenant model

Each organisation is a tenant.

Tenant-owned entities include `OrganisationId`.

Branch-owned entities include `BranchId`.

Warehouse-owned entities include `WarehouseId` where applicable.

The backend validates:

- user membership;
- organisation status;
- branch access;
- warehouse access;
- device status;
- module status;
- permission.

# Part 5 — Business Rules, Offline Synchronization, Conflicts, Accounting, and Inventory

## 52. General business rules

### BR-001
Every tenant-owned record must belong to an organisation.

### BR-002
Users may access only authorised organisations, branches, and warehouses.

### BR-003
Client totals are never authoritative.

### BR-004
Completed financial records are not silently deleted.

### BR-005
Corrections use reversal, return, note, or adjustment.

### BR-006
Sensitive actions create audit records.

### BR-007
Money uses decimal and currency.

### BR-008
Server timestamps use UTC.

---

## 53. Sales rules

### BR-009
A completed sale must contain at least one item.

### BR-010
The server calculates totals.

### BR-011
Paid amount cannot exceed due amount unless excess becomes advance.

### BR-012
Historical price remains unchanged.

### BR-013
Discount beyond limit requires permission.

### BR-014
Credit-limit override requires permission and reason.

### BR-015
Duplicate idempotency keys do not create duplicate sales.

---

## 54. Payment rules

### BR-016
Payment allocation cannot exceed available payment.

### BR-017
Payment allocation cannot exceed outstanding invoice unless advance handling is used.

### BR-018
Customer balances derive from ledger entries.

### BR-019
Supplier balances derive from ledger entries.

### BR-020
Accepted payments are corrected through reversal.

---

## 55. Inventory rules

### BR-021
Every stock change creates a movement.

### BR-022
Direct unexplained stock overwrite is forbidden.

### BR-023
Offline sales cannot exceed device allocation.

### BR-024
Transfers require source and destination.

### BR-025
Count variance requires adjustment.

### BR-026
Negative stock is not silently hidden.

### BR-027
Expired allocation cannot be used.

### BR-028
Revoked allocation cannot be used.

---

## 56. Accounting rules

### BR-029
Posted journals contain at least two lines.

### BR-030
Debit equals credit.

### BR-031
Posted journals are immutable.

### BR-032
Corrections use reversal.

### BR-033
Closed periods reject normal posting.

### BR-034
Journals retain source module and transaction.

### BR-035
The same source cannot post twice.

---

## 57. Synchronization rules

### BR-036
Offline writes save business records and outbox together.

### BR-037
Operations use client-generated UUIDs.

### BR-038
Operations include idempotency keys.

### BR-039
Server processing is idempotent.

### BR-040
Dependencies are processed in order.

### BR-041
Permanent rejection is not retried forever.

### BR-042
Pull uses incremental cursor.

### BR-043
Deleted synchronized records use tombstones where appropriate.

### BR-044
Financial records do not use last-write-wins.

---

## 58. Conflict rules

### 58.1 Financial conflict

Preserve the transaction.

Require reversal or adjustment.

### 58.2 Customer conflict

Use optimistic concurrency.

Allow:

- server version;
- client version with permission;
- merge;
- manual review.

### 58.3 Price conflict

Server controls current price.

Historical sale preserves used price.

### 58.4 Inventory conflict

Use movement reconciliation.

Do not overwrite central balance.

### 58.5 Permission conflict

Server permission wins.

### 58.6 Module-disabled conflict

Pending operations remain visible and require review.

---

- warehouse;
- device;
- product;
- condition;
- quantity;
- consumed;
- returned;
- effective;
- expiry;
- revocation;

```text
User creates sale offline

    ↓

    ↓

    ↓

    ↓

    ↓

```
